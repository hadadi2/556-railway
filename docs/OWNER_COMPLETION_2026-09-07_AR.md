## الإصلاحات في هذه الدفعة

1. **فحص الأسرار — direct reproduction.** وظيفة `secret-scan` في تشغيل GitHub رقم `34128764069` رفضت ثلاث قيم مصطنعة داخل اختبارات تنقيح المفاتيح وسياسة كلمة المرور. جرى فحص سياق كل قيمة. ملف `.gitleaksignore` يستثني البصمة التاريخية الدقيقة لكل واحدة، بما فيها الإيداع والمسار ورقم السطر. لا تعطيل للفاحص، ولا استثناء لمجلد الاختبارات، ولا كشف لقيم المفاتيح في هذا المستند. أي قيمة جديدة أو إيداع مختلف يبقى خاضعاً للكشف. [توثيق البصمات لدى Gitleaks](https://github.com/gitleaks/gitleaks#excluding-findings).
2. **مصدر رمز المصنع — direct reproduction.** دراسة غير مرتبطة بمنتج كانت ترسل الرمز إلى محرك البحث بمصدر `catalog` حتى بعد إدخاله يدوياً. الترحيل الإضافي `021_study_hs_source.sql` يحفظ الإقرار الصريح على الدراسة. الواجهة ترسل `manual` عند الإدخال اليدوي؛ الخادم يرفض ادعاء إثبات صورة من العميل، أو إقراراً لا يحدد الرمز. تغيير المنتج أو الرمز دون إقرار جديد يلغي المصدر اليدوي. إعادة حفظ صف قديم لا ترفعه إلى إقرار جديد؛ يبقى `unknown`. مصدر المنتج المملوك يبقى مسار الاحتياط. الإقرار لا يمنح شهادة صحة جمركية ولا يلغي التحقق المرجعي في المحرك.
3. **سباق زر التصنيف — direct reproduction.** اكتمال طلب يدوي قديم كان يعيد تفعيل الزر أثناء رفع صورة أحدث. أصبح اكتمال الزر مقيداً بجيل الصورة نفسه. اختبارات Node تشغّل دوال الواجهة الفعلية مع استجابات مؤجلة بترتيب معاكس.
4. **الواجهة الفعلية.** تدفق المتصفح يكتب رمز المصنع، ويحفظ الدراسة عبر HTTP الحقيقي، ويفحص `hs_code` و`hs_source` في استجابة الخادم قبل متابعة الإطلاق. مزود البحث في هذا التدفق محاكى؛ ليس إثبات جودة دراسة مدفوعة أو دقة صورة حقيقية.

## عوائق ألف دراسة فعلية بالتوازي

**static code review:** `silk_platform/study_runtime.py::max_concurrent` يضبط سقف المنصة الافتراضي بثلاث تشغيلات. `silk_research_runtime.py::max_concurrent` يضبط سقف `/research` المباشر بثلاث؛ السقفان منفصلان. تشغيلات المنصة لها مطالبة ذرية وطابور SQLite، لكن `silk_research.py::run_market` ينشئ مجموعة خيوط لوكلاء الدراسة الواحدة. عدد الدراسات النشطة لا يساوي عدد الخيوط أو نداءات المزودين.

اختبار `test_platform_capacity_2026_09_07.py` يدرج ألف صف مباشرة، ويستبدل المحرك، ويقيس ذروة ثلاث تشغيلات. لا يختبر استقبال ألف طلب HTTP أو ألف دراسة كاملة متداخلة زمنياً. لذلك لا يفي بطلب المالك، ولا يصلح رفع المتغير إلى 1000 لإعلان الإنجاز.

الإثبات المطلوب قبل اعتماد السعة:

1. قياس تكلفة الذاكرة والوقت ونداءات المزودين لدراسة فعلية ممثلة؛ الميزانية والحدود تُقرأ من حسابات التشغيل، لا تُخمن.
2. فصل استقبال الطلبات عن عمال البحث، مع حالة مشتركة قابلة للمطالبة الذرية عبر العمال وحفظ الحجز والإلغاء والنتائج عند إعادة التشغيل. النسخ المنفصلة من SQLite ليست مخزناً مشتركاً.
3. تنظيم التوازي الداخلي وحدود المزودين على مستوى الخدمة، حتى لا يتحول توازي الدراسات إلى عدد غير مضبوط من النداءات والخيوط.
4. اختبار قبول يبدأ ألف دراسة كاملة معاً عبر الواجهة البرمجية، ويثبت تداخل فترة تنفيذها، وصحة ملكية النتائج، وعدم ازدواج الخصم، واستمرار الواجهة أثناء الحمل، والتعافي من سقوط عامل. يجب تسجيل نوع المزود المستخدم صراحة؛ المحاكاة ليست إثباتاً لحدود الحساب الحقيقي.

لم تُنفّذ هذه البنية الموزعة في هذه الدفعة. شرط الألف ما زال مفتوحاً.
